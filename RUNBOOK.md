# Runbook — run it locally, then deploy it

Follow this top to bottom. It is written to be executed, not read.
Target: a live URL within 45 minutes of starting.

---

## Part 1 — Accounts (about 15 minutes)

Do all three before writing any code. If one of them is going to fail, it must fail now.

### 1. GitHub

Create a repository named `nkwanta`. Public is simplest — the examiner needs access.
If private, add the examiner as a collaborator.

### 2. Neon — the database

1. Sign up at neon.com with your GitHub account. No card required.
2. Create a project called `nkwanta`, region **Europe (Frankfurt)** — closest to Ghana.
3. Open the **SQL Editor** and run:

   ```sql
   CREATE EXTENSION IF NOT EXISTS postgis;
   SELECT postgis_version();
   ```

   A version string means the geography half of the project works. If this fails,
   stop and fix it — B05 cannot be built without it.

4. **Connection Details** → copy the **pooled** connection string. It looks like:

   ```
   postgresql://user:pw@ep-xxxx-pooler.eu-central-1.aws.neon.tech/nkwanta?sslmode=require
   ```

   Paste it somewhere safe. You need it twice.

### 3. Render — the application

Sign up at render.com with GitHub. Confirm you can reach **New +** → **Blueprint**.
Do not create anything yet.

## Part 2 — Run it locally (about 10 minutes)

### Check your Python version first

```bash
python --version
```

**Python 3.11 through 3.14 all work.** Every pinned dependency has a prebuilt wheel for
each of them, verified against PyPI on 12 August 2026.

This matters more than it sounds. Packages with C or Rust extensions — `asyncpg`,
`pydantic-core`, `SQLAlchemy` — are compiled from source when no matching wheel exists,
and that needs the MSVC C++ build tools plus a Rust toolchain. On Python 3.14 the
original pins had no wheels and the install failed with
`Microsoft Visual C++ 14.0 or greater is required`. The pins were moved forward to the
first versions that publish 3.14 wheels rather than asking anyone to install a compiler.
See D-015.

### Create and activate the virtual environment

The activation command differs by shell, and getting it wrong is the most common
stumble here.

**Git Bash / MINGW64 on Windows** — note `source`, and `Scripts` not `bin`:

```bash
python -m venv .venv
source .venv/Scripts/activate
```

**PowerShell:**

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

**CMD:**

```cmd
python -m venv .venv
.venv\Scripts\activate.bat
```

**macOS / Linux:**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

> Running `.venv/Scripts/activate` **without** `source` in Git Bash executes it in a
> subshell that exits immediately, so your shell is never activated. The symptom is
> `bash: pip: command not found`.

Confirm it worked — the path must point inside `.venv`:

```bash
which python      # Git Bash / macOS / Linux
where python      # PowerShell / CMD
```

### Install

Use `python -m pip`, not bare `pip`. It works whenever `python` works, which avoids
PATH problems altogether.

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### Environment file

```bash
cp .env.example .env        # CMD/PowerShell: copy .env.example .env
```

Open `.env` and paste your Neon string into `DATABASE_URL`. Paste it **exactly as Neon
gave it** — the application rewrites it for the async driver on its own.

```bash
alembic upgrade head        # creates the PostGIS extension
uvicorn app.main:app --reload
```

Open <http://127.0.0.1:8000>. You want a green dot and `PostGIS 3.x`.

| Endpoint | What it is for |
|---|---|
| `/` | Status page |
| `/health` | Liveness. Never touches the database. This is what the keep-warm ping hits. |
| `/ready` | Readiness. Checks the database and PostGIS. |
| `/docs` | Interactive API documentation, generated by FastAPI |

Run the tests:

```bash
pytest
```

22 tests, all passing, no database required.

## Part 3 — Deploy (about 15 minutes)

```bash
git add .
git commit -m "B01: scaffold, health checks, PostGIS migration"
git push -u origin main
```

In Render: **New +** → **Blueprint** → select the repo. It reads `render.yaml` and
proposes one free web service.

### Environment variables — the full list

`render.yaml` declares all six. Four carry their values; two do not, and this is the
complete record of what must be supplied by hand.

| Key | Where the value comes from | Why |
|---|---|---|
| `DATABASE_URL` | **You paste it.** Neon pooled connection string | A credential. Never committed — `sync: false` in the blueprint declares the variable without carrying its value. |
| `JWT_SECRET` | **Render generates it.** `generateValue: true` | Signs authentication tokens. A generated random value beats a human-chosen one, and it stays stable across deploys. |
| `ENVIRONMENT` | `render.yaml` → `production` | Switches the app from warning about the default JWT secret to refusing to start with it |
| `PYTHON_VERSION` | `render.yaml` → `3.12.6` | Pinned so the build is reproducible |
| `CLUSTER_RADIUS_METRES` | `render.yaml` → `300` | Tunable without a redeploy — see TD-03 |
| `CLUSTER_WINDOW_MINUTES` | `render.yaml` → `30` | As above |
| `CONFIDENCE_HALF_LIFE_MINUTES` | `render.yaml` → `45` | As above |

So in the Render dashboard there is exactly **one** value to type: `DATABASE_URL`.

**Locally** you need `DATABASE_URL` in `.env`. `JWT_SECRET` may be left at the default —
the app warns but runs. To generate one anyway:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

> **The app refuses to start in production while `JWT_SECRET` is the default.** That is
> deliberate. A live service signing tokens with a secret published in the repository is
> not degraded, it is unauthenticated — so it fails loudly at boot rather than quietly
> at runtime.

Deploy. First build takes 3–5 minutes. Then check:

```
https://<your-service>.onrender.com/health     -> {"status":"ok", ...}
https://<your-service>.onrender.com/ready      -> {"status":"ok","postgis":"3.x"}
https://<your-service>.onrender.com/           -> green dot
https://<your-service>.onrender.com/docs       -> API documentation
```

**When `/ready` returns `postgis`, B01 is done and the largest risk in the schedule is
retired.** Everything after this is an increment on a deployment that already works.

## Part 4 — Two things to do immediately after the first successful deploy

### Keep-warm ping

Render free services sleep after **15 minutes** idle and take **30–60 seconds** to wake.
An examiner who waits a minute concludes your application is broken.

Go to cron-job.org (free), create a job hitting `https://<your-service>.onrender.com/health`
every 10 minutes. `/health` does not touch the database, so this costs no Neon compute.

### Tell the examiner anyway

Put this at the top of `Deployment_and_Source_Links.txt`:

> This application is deployed on a free-tier host. If it has been idle, the first
> request may take up to 60 seconds while the instance wakes. Subsequent requests are
> immediate.

Belt and braces. The ping can lapse; the sentence cannot.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `TypeError: connect() got an unexpected keyword argument 'sslmode'` | Raw libpq URL reached asyncpg | Should be impossible — `app/config.py` strips it. Check you edited `DATABASE_URL` and not something else. |
| `alembic: DATABASE_URL is not set` | No `.env`, or running from the wrong directory | `cp .env.example .env`, run from the repository root |
| `/ready` says `postgis: missing` | Extension never created | Run `CREATE EXTENSION IF NOT EXISTS postgis;` in the Neon SQL editor |
| `/ready` says `database: unreachable` | Wrong string, or the project is suspended | Re-copy the **pooled** string from Neon |
| Render build fails on `alembic upgrade head` | `DATABASE_URL` not set in Render | Add it in the dashboard, then **Manual Deploy → Clear build cache & deploy** |
| Render deploy succeeds, first request hangs ~50 s | Free tier cold start | Expected. See Part 4. |
| `AttributeError: module 'bcrypt' has no attribute '__about__'` | `passlib` reinstalled from somewhere | Remove it. This project uses `bcrypt` directly — see `app/security.py`. |
| `bash: pip: command not found` (Git Bash) | Ran `.venv/Scripts/activate` without `source`, so the shell was never activated | `source .venv/Scripts/activate`, then use `python -m pip` |
| `error: Microsoft Visual C++ 14.0 or greater is required` | pip is compiling a C extension because no wheel matches your Python | Should not happen with the current pins. If it does, `python -m pip install --only-binary :all: -r requirements.txt` will fail loudly instead of trying to compile, naming the package at fault. |
| `error: linking with link.exe failed` / `maturin failed` | Same cause, Rust side — `pydantic-core` compiling from source | As above. Confirm you pulled the latest `requirements.txt`. |
| `uvicorn: command not found` | Virtual environment not active | Re-activate, or run `python -m uvicorn app.main:app --reload` |
| `ModuleNotFoundError: No module named 'app'` | Running from the wrong directory, or an old `pytest.ini` without `pythonpath = .` | Run from the repository root — the folder containing `app/` and `requirements.txt`. `pytest.ini` sets `pythonpath = .` so both `pytest` and `python -m pytest` work. |
