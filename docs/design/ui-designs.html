Nkwanta — UI/UX design specification

A road incident reporting and dispatch system for urban Ghana.

Theophilus Caesar · 22424543 · CSCD602 Advanced Software Engineering · University of Ghana · 13 August 2026

1. Design principles

Four constraints shaped every screen, and each traces to a requirement rather than a preference.

PrincipleComes fromWhat it changed
Nothing asks a driver to type NFR-3 Reporting is voice-first and one-thumb. Type selection is chips, not a dropdown. Location defaults to GPS.
Works on a poor connection NFR-2 Installable, offline shell, and reports queue locally when there is no signal. The map degrading does not take the page with it.
A score must be interrogable Design review Every confidence figure opens onto the reports behind it, with each reporter's standing and contribution. A number an officer cannot question is one they learn to ignore.
A reporter is never exposed NFR-4, NFR-4a Voice sharing is off by default with a plain-language explanation. Reported parties are never shown to other users.

Colour carries meaning, never decoration. The four status colours map one-to-one onto incident states, so a pin's colour and a badge's colour always mean the same thing. Neutrals are tinted very slightly green rather than pure grey, which keeps the palette coherent without anyone noticing why.

Avatars

Every avatar in this specification is initials on a coloured disc, with the colour derived deterministically from the user id. Nobody uploads a profile photograph, and that is a decision rather than a feature that ran out of time.

ReasonDetail
It would work against NFR-4a A face attached to a name that appears in an officer's evidence list makes a reporter easier to identify. That requirement exists precisely to prevent it — it is why voice notes default to private.
Personal data with no operational purpose No decision in the system is improved by knowing what a reporter looks like.
Storage More binary in PostgreSQL, which is already the debt item most likely to fail first under real adoption (TD-19).
Moderation User-uploaded images of people need reviewing. There is no moderator, and a feature that assumes one it does not have is a liability.
A staff-only variant was considered — photographs for wardens and officers, who are public-facing and whose recognition is useful, with initials for commuters. It is a defensible position and was set aside as unnecessary complexity for no gain the system actually needs.

States every view must have

StateTreatment
LoadingSkeleton rows matching final layout — never a spinner over a blank panel
EmptyA sentence saying what to do next, not "no data". "No alerts. Follow a road below to be warned about it."
ErrorWhat failed and what to do, inline beside the control that failed
OfflinePersistent banner; queued reports shown with a pending marker
DisabledSubmit stays disabled until required fields validate, with the reason stated

Warden assignment. One job, two outcomes, both one tap. The reporter's voice note plays here — a warden being sent somewhere should hear why. The consequence of the decision is stated before it is made.
Warden seesWarden cannot

Both outcomes are equally prominent. Making "nothing there" harder to reach than "road clear" would bias the record, and that record is what drives every reporter's standing.

7. Offline behaviour

SituationWhat happens
App opened with no signalShell and last-known incidents load from cache; a banner says the data may be stale
Report filed with no signalStored locally, shown in the list with a pending marker, sent automatically when signal returns
The same report retriedCarries the idempotency key generated at capture, so a retry cannot create a duplicate or inflate an incident's confidence
Voice note filed offlineQueued with the report and uploaded after it, once the report has an id
Signal returnsQueue drains oldest first; failures stay queued and are retried on the next connection
This is the reason the application is a PWA rather than a website. Someone standing at a flooded junction with one bar is exactly the user this system exists for, and NFR-2 requires it to work for them. The idempotency keys it depends on were built into report intake at B04, months before there was a client to use them.

8. What the design needs that the API does not yet have

Most of this specification is served by endpoints that already exist and are tested. Three are not, and they are listed here so they are planned rather than discovered mid-build.

Needed forEndpointNotes
Edit display name PATCH /auth/me Display name only. Role and email must not be accepted in the body — the same reasoning as registration, where the field simply does not exist rather than being validated away.
Change password POST /auth/me/password Requires the current password, so an unlocked borrowed phone cannot lock its owner out. Reuses the existing 8–72 byte rule and the bcrypt helpers from B03.
Deactivate an account PATCH /auth/users/{id} Admin only. is_active already exists on the model and is already checked on every request — there is simply no route to set it.
Email cannot be changed, and that is a decision rather than an omission. It is the login identifier, so changing it needs a verification message to prove the new address belongs to the user. This system has no email delivery — the same constraint that rules out password reset (TD, scheduled). Presenting the field as locked with the reason stated is more honest than hiding it.

9. Accessibility and constraints

Touch targets44 px minimum on mobile
ContrastWCAG AA for body text; status colours paired with text, never colour alone
KeyboardEvery action reachable by tab; visible focus rings; modals trap focus and close on Escape
Screen readersLabelled inputs, live regions for alerts, meaningful button names
MotionRespects prefers-reduced-motion
LanguageEnglish only. Twi and Ga are in the evolution plan — a real gap for this user base, recorded rather than glossed
